# Firebase, вход и GPS — развёртывание в Google AI Studio

## Что восстановлено

Прежний экран Silk Road с входом через Google и гостевым входом Firebase. Отдельных кодов доступа и локальных CRM-сеансов больше нет. Администратор — подтверждённый Google-аккаунт **ti07kz@gmail.com**. Гость не получает административные права. Сохранённые профили других сотрудников не пересоздаются и не переписываются при входе; старое значение admin у постороннего пользователя или демо-профиля не даёт прав владельца.

Используется существующая конфигурация из firebase-applet-config.json:

- проект: logisticsapp-216d5;
- база Firestore: ai-studio-12b741bf-685d-4d79-a3b0-c771090926cd;
- Firebase Authentication и прежние UID пользователей;
- прежние коллекции users, shipments, regional_orders, saved_trucks, saved_delivery_contacts и подколлекции shipments/{id}/logs.

Не создавайте новый Firebase-проект/базу при импорте в AI Studio. Не меняйте идентификаторы в firebase-applet-config.json. Записи server/data с этого компьютера автоматически в Firebase не загружаются.

Изменения заявки записываются с сохранением остальных полей и того же ID документа. Координаты новых обновлений хранятся отдельно в gps_tracking; согласие, точка старта и история переживают перезапуск Cloud Run. Сессии водителей находятся в driver_sessions, курсор Telegram — в bot_state. Прежние GPS-поля и история в regional_orders остаются читаемыми для совместимости и не удаляются.

### Если CRM выглядела пустой после обновления

Исправлена зависимость обычных данных CRM от Firebase Admin на сервере: перевозки, сотрудники и справочники снова читаются напрямую через Firebase SDK под текущей учётной записью, как в прежнем приложении. Их редактирование также использует существующие правила Firestore. Для отображения этих разделов на localhost не нужен приватный ключ сервисного аккаунта. Профили и документы не пересоздаются; локальные файлы и кэши не импортируются поверх базы.

Администратор читает региональные заявки напрямую из прежней коллекции. Сотрудники получают эти заявки через сервер, скрывающий GPS-поля. Для изменения региональных заявок, трекинга, Telegram, серверных интеграций и загрузки файлов по-прежнему нужен настроенный серверный доступ из шага 2 ниже. Права на GPS не расширяются.

Ошибка загрузки и пустой временный кэш больше не выглядят как отсутствие записей. CRM показывает сообщение с повторной попыткой; повторное подключение обновляет список. Факт удаления данных по одному пустому экрану определить нельзя. Саму боевую базу и правила в процессе этого исправления не изменяли.

Ошибка auth/popup-closed-by-user означает, что окно Google закрылось до завершения входа. Откройте localhost:3000 в обычном браузере, нажмите Sign in with Google и завершите выбор рабочего аккаунта. Для auth/popup-blocked разрешите всплывающие окна. Эти сообщения относятся к авторизации; чтение данных начинается после успешного входа.

## Развёртывание

### Получить изменения из GitHub

В существующем приложении Google AI Studio откройте Settings → GitHub и получите изменения из ветки main репозитория teimurkz/AILog. Если есть несохранённые изменения в AI Studio, сначала сохраните их; при конфликте сравните обе версии. Синхронизация обновляет исходный код, а боевой адрес обновляется после повторного Deploy. Не создавайте новый Firebase-проект при синхронизации.

В Git передаются код, тесты, пример переменных окружения и правила Firebase. Секреты из локального .env нужно задать отдельно в серверной среде; актуальные заявки и профили загружаются из существующего Firebase. После получения кода выполните шаги ниже: само обновление репозитория не публикует правила Firestore и не подключает Telegram webhook.

1. Обновите существующее приложение в Google AI Studio, сохранив его Firebase-конфигурацию. Сборка: npm run build; запуск: npm start. Express использует выданный Cloud Run порт PORT.
2. У сервисного аккаунта Cloud Run должен быть доступ к существующей Firestore (роль Cloud Datastore User) и бакету Firebase Storage для документов. На Cloud Run используется Application Default Credentials — приватный ключ не нужен в клиентском коде. На локальном компьютере для проверки серверных API настройте ADC или GOOGLE_APPLICATION_CREDENTIALS с путём к сервисному аккаунту этого проекта.
3. Вместе с обновлением приложения опубликуйте firestore.rules именно в указанной существующей именованной базе. firebase.json и .firebaserc уже указывают правильный проект и базу. Можно использовать Firebase Console или Firebase CLI: firebase deploy --only firestore:rules --project logisticsapp-216d5.
4. В Firebase Authentication сохраните Google и Anonymous providers и добавьте адрес приложения Cloud Run в Authorized domains, если его ещё нет.
5. В секретах серверной среды задайте прежний TELEGRAM_BOT_TOKEN и новый случайный TELEGRAM_WEBHOOK_SECRET (латинские буквы, цифры, _ и -). CRM_STORAGE_MODE=firebase — режим по умолчанию. Не задавайте local на Cloud Run.
6. TELEGRAM_WEBHOOK_URL должен быть https://<адрес-приложения>/api/driver/telegram/webhook. После публикации выполните npm run telegram:webhook в среде с этими секретами. Скрипт устанавливает max_connections=1 и сохраняет ожидающие обновления Telegram. Он не запускается при сборке и не запускался при подготовке этих изменений. Остановите прежний polling-процесс этого бота.
7. Войдите своим Google-аккаунтом и проверьте существующие заявки, список сотрудников и карту. Другой сотрудник или гость может пользоваться разрешёнными разделами CRM, но не получает координаты ни через карту, ни через прямой API, ни через Firestore.

Правила regional_orders изменены вместе с API: сотрудники читают заявки через сервер, который убирает GPS-поля. Firestore не умеет скрывать отдельные поля документа; прямое чтение этого документа разрешено только владельцу. Поэтому приложение и правила нужно выпускать согласованно: старая версия клиента с прямым чтением regional_orders не совместима с новыми правилами. Остальные коллекции и их данные не переносятся и не очищаются.

Webhook подходит для Cloud Run: обработка идёт в рамках входящего запроса и не требует постоянно работающего локального компьютера. Повторное обновление Telegram не применяет изменения повторно. Firestore подтверждает сохранение до успешного HTTP-ответа. Транзакционные повторы не дублируют сообщения и события.

При недоступной Firebase сервер возвращает ошибку, а не переключается на пустую локальную базу. Сборка и тесты не публикуют правила и не изменяют боевые данные.

## Проверка

- npm run test:crm — чтение прежних документов, пустой кэш, отказ доступа, прерванное соединение и повторная загрузка без обращения к боевой базе.
- npm run test:gps — сценарии согласия, Telegram Live Location, завершения рейса, API, Socket.IO/SSE и проверки доступа по Firebase-идентичности. Firebase-верификатор подменён только в тестовом сервере.
- npm run test:firebase — контрактные проверки транзакций с изолированным хранилищем: сохранение полей, восстановление GPS, прежняя история, повторные обновления и отказ записи.
- npm run lint — проверка типов.
- npm run build — сборка приложения.

Для полноценной проверки Google-входа и Firestore нужен настроенный Firebase-проект и сервисный аккаунт. Тесты используют временные данные и не входят за реальных сотрудников.

## Как работает GPS

Водитель открывает Telegram-бота, выбирает существующую заявку и даёт согласие. Затем отдельно включает 📎 → Геопозиция → Транслировать геопозицию, разрешая Telegram доступ к геопозиции в фоне. Бот не может включить GPS телефона сам. При ограниченном сроке трансляцию нужно продлевать до завершения рейса.

Маршрут начинается в первой GPS-точке машины, идёт по дорогам до города назначения, а зелёная линия показывает фактическую историю. OSRM_ROUTE_URL задаёт сервис маршрутизации; он получает координаты старта и назначения. При его недоступности путь помечается ориентировочным. Маркер всегда показывает полученную геопозицию.

«Завершить рейс» закрывает заявку и прекращает приём координат. История остаётся доступна администратору. Резервная страница /gps получает только реквизиты рейса и передаёт GPS после уже подтверждённого согласия, пока страница телефона активна.
