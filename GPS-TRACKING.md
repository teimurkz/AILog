# GPS и CRM через Firebase, интерфейс в Google AI Studio

Приложению в AI Studio больше не требуется собственный Express-сервер. Обычные данные CRM читаются через Firebase Web SDK. Региональные заявки сохраняются через HTTPS-функцию `crmApi` в Firebase; она проверяет тот же Firebase-вход и сохраняет документы в прежней именованной базе. Telegram отправляет координаты в эту же функцию. Карта администратора подписана на изменения Firestore, без Socket.IO и постоянного серверного соединения.

**Получение кода из GitHub само по себе не публикует Cloud Functions.** До однократной настройки Firebase ниже приём Telegram и изменение региональных заявок работать не будут. Firestore и Authentication сами по себе не исполняют обработчик Telegram. Для публикации Cloud Functions нужен тариф [Blaze](https://firebase.google.com/docs/functions/get-started). При подготовке кода тариф не подключался, функции и правила не публиковались, webhook не менялся.

## Существующая база и пользователи

Сохраняется `firebase-applet-config.json`:

- проект: `logisticsapp-216d5`;
- именованная база: `ai-studio-12b741bf-685d-4d79-a3b0-c771090926cd`;
- прежние Firebase Authentication, UID, профили и коллекции CRM;
- прежние ID заявок, дополнительные поля и GPS-история.

Не создавайте новый Firebase-проект при импорте в AI Studio. Локальные файлы `server/data` не импортируются в Firebase. Новый документ получает уникальный ID; создание заявки с уже существующим ID отклоняется, а редактирование сохраняет остальные поля документа.

Вход остаётся через Google или гостевой вход Firebase. GPS доступен только подтверждённому аккаунту `ti07kz@gmail.com`. Сотрудники получают региональные заявки через Firebase-функцию с удалёнными GPS-полями. Firestore не скрывает отдельные поля документа, поэтому прямое чтение `regional_orders` с прежними GPS-полями и `gps_tracking` разрешено только администратору. Профили сотрудников при входе не пересоздаются.

## Однократная публикация в Firebase

Команды выполняются из корня этого репозитория в терминале с доступом к существующему Firebase-проекту, например в Google Cloud Shell. Используйте рабочий Google-аккаунт и прежний проект. Не передавайте ключи сервисного аккаунта в клиентский код.

1. Проверьте, что в существующем Firebase-проекте включён Blaze. Подключение оплаты выполняет владелец проекта.
2. Установите зависимости и войдите в Firebase CLI:

   ```sh
   npm ci
   npm ci --prefix functions
   npx firebase-tools login
   ```

3. Сохраните два секрета непосредственно в Firebase. В интерактивном запросе первого укажите прежний токен вашего Telegram-бота. Для второго используйте случайную строку из латинских букв, цифр, `_` и `-` длиной до 256 символов. Сохраните её для шага 5.

   ```sh
   npx firebase-tools functions:secrets:set TELEGRAM_BOT_TOKEN --project logisticsapp-216d5
   npx firebase-tools functions:secrets:set TELEGRAM_WEBHOOK_SECRET --project logisticsapp-216d5
   ```

4. Опубликуйте код функций и согласованные правила доступа:

   ```sh
   npx firebase-tools deploy --only functions:crm,firestore:rules --project logisticsapp-216d5
   ```

   `firebase.json` задаёт codebase `crm` и прежнюю именованную базу. Перед публикацией функция автоматически собирается в `functions/lib`. Исходные локальные JSON, секреты и файлы пользователей в пакет не входят. Сервисному аккаунту функции нужны права на прежнюю Firestore и Storage для документов. Firebase Admin использует полномочия среды Firebase, а не ключ из браузера.

   Регион и имя функции заданы в `firebase-functions-config.json`: `asia-east1`, `crmApi`. Ожидаемый адрес проверки:

   [Проверить функцию CRM](https://asia-east1-logisticsapp-216d5.cloudfunctions.net/crmApi/api/health)

   Ответ должен быть `{"service":"silk-road-crm","status":"ok"}`. Это проверка запуска, не проверка прав на данные. Сверьте URL с выводом Firebase CLI. Если среда выдала другой адрес, задайте публичный `VITE_CRM_API_BASE_URL` для интерфейса и `TELEGRAM_WEBHOOK_URL` для настройки бота.

5. Подключите Telegram к Firebase. В локальном `.env` либо переменных терминала задайте тот же `TELEGRAM_BOT_TOKEN` и тот же `TELEGRAM_WEBHOOK_SECRET`, затем выполните:

   ```sh
   npm run telegram:webhook
   ```

   По умолчанию будет использован адрес:
   `https://asia-east1-logisticsapp-216d5.cloudfunctions.net/crmApi/api/driver/telegram/webhook`.
   Если в старом `.env` остался `TELEGRAM_WEBHOOK_URL` с адресом AI Studio/Cloud Run, замените его на этот адрес. Скрипт сохраняет очередь Telegram, включает обновления Live Location и `max_connections=1`. Остановите прежний polling-процесс этого бота. Нельзя одновременно получать сообщения одного бота несколькими polling-процессами и webhook.

6. Получите ветку `main` в существующем приложении AI Studio, перезапустите предпросмотр и выполните Deploy для опубликованного интерфейса. `npm run dev` запускает только Vite; `npm run build` собирает только интерфейс; `npm start` / `npm run preview` показывают сборку. Функция Firebase публикуется отдельно и продолжает работать при закрытом браузере.

7. Войдите через Google рабочим аккаунтом, создайте региональную заявку и пройдите маршрут ниже. Проверьте отображение старых данных и отсутствие доступа к GPS у обычного сотрудника. Если Firebase Authentication выдаёт `auth/unauthorized-domain`, добавьте фактический домен интерфейса в Authorized domains прежнего проекта, сохранив Google и Anonymous providers.

## Работа водителя и карты

Водитель открывает Telegram-бота, выбирает существующую заявку и подтверждает согласие на передачу геопозиции. После этого включает **скрепка → Геопозиция → Транслировать геопозицию**. Бот не может сам включить GPS телефона. Для обновлений в фоне нужны разрешения Telegram в настройках телефона; трансляцию с ограниченным сроком нужно продлевать.

Webhook Firebase проверяет секрет Telegram и аккаунт водителя, привязанный к рейсу. Координаты, согласие и история записываются транзакционно в существующую Firestore. Новый GPS хранится в закрытой `gps_tracking`; сеансы водителя — в `driver_sessions`, подтверждённые обновления Telegram — в `bot_state`. Повтор запроса не применяет обновление второй раз. Прежние GPS-поля в заявках не стираются.

Карта администратора получает уведомления Firestore и обновляет положение. Маршрут начинается в первой настоящей GPS-точке машины и заканчивается в городе назначения. Дорожная геометрия запрашивается в рамках выполняющегося запроса Firebase; при недоступности маршрутизатора показывается ориентировочный путь с соответствующей пометкой. Устаревание сигнала отображается без подмены координат.

«Завершить рейс» в Telegram прекращает приём GPS для этой заявки. Запоздалые координаты и кнопки от старого рейса не открывают его заново. Публичная ссылка на заявку не позволяет отправить чужие координаты или завершить чужой рейс. Старый адрес `/gps` теперь направляет водителя в Telegram.

## Проверки и диагностика

- `npm run lint` — проверка типов.
- `npm run lint:functions` — отдельная проверка типов Firebase-функции после установки её зависимостей. Интерфейс AI Studio не требует установки пакета функций.
- `npm run build` — сборка статического интерфейса.
- `npm run build:functions` — сборка Firebase-функции без публикации.
- `npm run test:functions` — после сборки проверяет HTTP-обработчик Firebase, CORS, запрет запросов без авторизации, защиту webhook, соединение GPS по ID и устаревание сигнала. Реальные данные и сообщения не используются.
- `npm run test:gps` — согласие, создание заявки без перезаписи существующей, обновления Telegram, завершение, роли и запросы между разными доменами.
- `npm run test:firebase` — сохранение прежних документов и профилей, транзакционные повторы, восстановление GPS и маршрутизация без локальных файлов.
- `npm run test:crm` — загрузка CRM и ошибки соединения без подмены базы пустыми данными.

Для необязательного отдельного локального сервера оставлены `npm run dev:server`, `npm run build:server` и `npm run test:server`. Собранный сервер хранится вне `dist`, чтобы статический интерфейс не публиковал серверный код. Он не нужен для GPS через Firebase.

«Не удалось связаться с Firebase Cloud Functions» означает проблему соединения или отсутствие опубликованной функции. Ответ 401 означает незавершённый Firebase-вход; 403 — недостаточные права; сообщение о недоступности Firestore требует проверки прав сервисного аккаунта именно на существующую именованную базу. Эти ошибки не означают удаления записей. При отказе Firebase код не переключается на локальный JSON.

Перенос GPS не запускает старые фоновые таймеры рассылок/синхронизации внутри HTTP-функции. Если нужны автоматические задания по расписанию, их следует отдельно оформить как scheduled functions; закрытый браузер не должен выполнять эту работу.

Официальные документы: [HTTP-функции Firebase](https://firebase.google.com/docs/functions/http-events), [секреты функций](https://firebase.google.com/docs/functions/config-env), [подписки Firestore](https://firebase.google.com/docs/firestore/query-data/listen).
