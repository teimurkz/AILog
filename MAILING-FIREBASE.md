# Авторассылка складского отчета через Firebase

## Что исправлено

HTTP-функция `crmApi` сама по себе не запускает расписание. Зелёный переключатель в старом интерфейсе показывал лишь сохранённую настройку, а не работу службы. После перехода на статический интерфейс AI Studio прежний серверный таймер не выполнялся.

Теперь `warehouseMailing` вызывается Cloud Scheduler раз в минуту, читает сохранённое расписание и активных получателей из **существующей именованной базы** `ai-studio-12b741bf-685d-4d79-a3b0-c771090926cd` проекта `logisticsapp-216d5`. Время 09:00 в Asia/Almaty соответствует 04:00 UTC. Браузер для рассылки не нужен.

Новые служебные документы: `mailing_scheduler/warehouse` (состояние службы) и `mailing_runs/{id}` (выполнение задания). Они доступны только серверу по действующим правилам Firestore. База, пользователи, заявки, SMTP-настройки и получатели не заменяются и не очищаются. Старые файлы JSON используются только при явно заданном `CRM_STORAGE_MODE=local`.

## Публикация

Обновить только приложение в AI Studio недостаточно: нужно отдельно опубликовать Firebase-функции. Из актуальной ветки `main`, в терминале с доступом к существующему проекту:

```sh
npm ci
npm --prefix functions ci
firebase deploy --only functions:crmApi,functions:warehouseMailing --project logisticsapp-216d5
```

Сборка функций выполняется автоматически перед публикацией. Firebase CLI создаёт связанное задание Cloud Scheduler; не нужно создавать второй cron или публично открывать функцию расписания. Требуются действующий Blaze (он уже подключён), включённый Cloud Scheduler API и права аккаунта публикации на создание функции/задания. Рабочий сервисный аккаунт функции должен читать/писать существующую Firestore. SMTP берётся из настроек CRM; секреты Telegram остаются у `crmApi`.

Затем обновить `main` и опубликовать интерфейс в AI Studio. Через 1–2 минуты в разделе авторассылки должна появиться свежая проверка и надпись «Служба рассылки работает». Если сигнала нет больше пяти минут, интерфейс показывает предупреждение. Журналы Cloud Functions для `warehouseMailing` и Cloud Scheduler показывают ошибки запуска или прав доступа.

Первый запуск создаёт точку отсчёта и не досылает пропущенное письмо задним числом. Если публикация сделана после сегодняшних 09:00, ближайшая ежедневная отправка — завтра в 09:00. Проверить подключение кнопкой SMTP можно без отправки письма. «Отправить сейчас», «Отправить по настройкам» и «Тест» отправляют настоящие письма.

## Поведение при сбоях

- Короткую задержку запуска до 90 минут служба компенсирует. Старые дни не догоняет.
- Для ежедневных, рабочих, еженедельных и выбранных дней используется одно задание на дату/время. Тестовый интервал хранится отдельно для каждого интервала. Режим «при изменении» сравнивает содержимое свежего отчёта с предыдущим; первая проверка только запоминает исходное состояние.
- Транзакционная блокировка и журнал в Firestore защищают от параллельных запусков и повторов после перезапуска функции.
- При временной ошибке **до передачи письма** разрешены максимум три попытки задания, с задержками 5 и 10 минут. Gmail может использовать альтернативный порт при такой ошибке. Порт 465 всегда использует TLS сразу, 587 — STARTTLS; проверка сертификата включена.
- Если соединение оборвалось после возможной передачи письма, результат отмечается как неизвестный и автоматического повтора нет. SMTP не гарантирует строго однократную доставку. Частичная приёмка получателей также не вызывает повтор всего списка.
- Время успешной отправки у получателя обновляется только после приёмки письма SMTP. Это ещё не подтверждение попадания во «Входящие»; возможны фильтры спама или поздний отказ принимающей стороны.
- Ошибки Firestore больше не скрываются локальными файлами. Успешные записи журнала не содержат `undefined`, из-за которого Firestore мог отвергать запись. Сбой обновления журнала после отправки не приводит к повторной отправке письма.
- При недоступности полного свежего Excel из Google Sheets рассылка откладывается; неполная запасная выгрузка не рассылается.

## Проверки без реальных писем

```sh
npm run test:mailing
npm run lint
npm run lint:functions
npm run build:functions
npm run test:functions
npm run build
```

Тесты используют искусственные данные и заменяют Firestore/SMTP. Они проверяют время, пропуски, повторы, параллельные запуски, прерывание во время отправки, выключение расписания во время подготовки, сохранение записей и ошибки TLS.

Документация: [задания Firebase по расписанию](https://firebase.google.com/docs/functions/schedule-functions), [SMTP и TLS в Nodemailer](https://nodemailer.com/smtp).
